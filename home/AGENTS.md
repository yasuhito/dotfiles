# グローバルなエージェント向け指示

- em dash「—」は決して使用せず、代わりに通常の dash「-」を使用する
- コミットメッセージを書くときは、エージェント名を共同作者として絶対に自動追加しない
- CHANGELOG.md ファイルや、自動生成としてマークされているファイルを手動で変更しない
- 技術的な意思決定では、開発コストをあまり重視しない。
  代わりに、品質、単純さ、堅牢性、スケーラビリティ、長期的な保守性を優先する。
- 一度限り、または頻度の低い運用作業では、最も単純で直接的な end-to-end の手順から始める。直接的な手順によって、追加の仕組みを正当化する具体的な障害や繰り返し発生する必要性が明らかにならない限り、ラッパー、コントロールプレーン、ポリシーレイヤー、独自の検証機構、自動化を構築しない。
- バグを修正するときは、必ず、エンドユーザーが体験する状況にできる限り近い E2E 環境でバグを再現することから始める。
  これにより本当の問題を確実に見つけ、修正によって実際にその問題を解決できる。
- 製品を end-to-end でテストするときは、目にする UI を厳しく吟味し、ピクセル単位の完璧さを徹底的に追求する。
  明らかにおかしく見えるものがあれば、取り組んでいることに直接関係していなくても、その過程で修正するよう努める。
- エンジニアリングの卓越性にも同じ高い基準を適用する。すなわち、lint、テスト失敗、テストの不安定性である。
  そのいずれかを見つけた場合は、現在取り組んでいることが原因でなくても、必ず修正する。
- 「dynamic workflows」、「ultra code」、または大規模なサブエージェント群を即座に起動するハーネス機能を使用する前に、必ずトレードオフを説明し、ユーザーから明示的な承認を得る。

## このファイルのメンテナンス

このプロジェクトで、今後ほぼすべてのエージェントセッションに役立つ知識をこのファイルに記載する。
コードベースを見ればわかることは繰り返さず、代わりに信頼できる正式なファイルやコマンドを示す。
新しい項目を追加するよりも、既存の項目の書き直しや削減を優先する。
このファイルを更新するときは、すべてのエージェントに対してこの基準を維持し、項目を簡潔に保つ。
